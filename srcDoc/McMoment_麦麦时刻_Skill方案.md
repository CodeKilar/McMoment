# McMoment 麦麦时刻

> 不只是帮你点麦当劳，而是根据你此刻的时间、位置、状态和同行者，安排一次最合适的麦当劳体验。

## 1. 项目概述

### 1.1 项目名称

- 中文名称：**麦麦时刻**
- 英文名称：**McMoment**
- 项目类型：基于麦当劳 MCP 的情境感知型生活服务 Skill

### 1.2 一句话介绍

McMoment 能够根据用户主动提供的时间、位置、预算、饮食偏好及同行信息，判断当前应该**什么时候吃、去哪家店、选择哪种取餐方式、吃什么以及如何使用优惠权益**，并通过麦当劳 MCP 完成真实计价、下单、活动预约和订单追踪。

### 1.3 核心定位

传统点餐助手通常在用户已经决定“我要吃什么”之后工作，而 McMoment 在用户只描述当前状态或接下来要做的事情时，就可以主动完成整个决策过程。

例如用户只需要说：

> 我刚健身完，下午一点有会，帮我安排午饭。

McMoment 可以进一步完成：

1. 根据用户提供的时间和可用时长确认约束；
2. 根据用户提供的位置和目标地点估算履约要求；
3. 查询当前天气，并结合用户的出行偏好选择外送、到店或得来速；
4. 根据用户提供的营养目标进行筛选；
5. 查询真实门店、菜单、营养数据和优惠券；
6. 生成满足预算、热量、蛋白质和时间要求的候选方案；
7. 调用实时计价工具验证最终价格；
8. 在用户确认后创建真实订单；
9. 追踪订单，并向用户反馈订单状态。

## 2. 项目背景与问题

麦当劳 MCP 已经提供了丰富的真实业务能力，包括：

- 附近门店与配送门店查询；
- 当前门店可售菜单查询；
- 套餐组成、商品替换和部分餐品特制；
- 餐品营养信息；
- 优惠券领取与查询；
- 积分、商城兑换和积分抽奖；
- 实时价格计算；
- 麦乐送、到店取餐、团餐和得来速下单；
- 历史订单、订单状态和取消订单；
- 活动日历和主题活动预约。

如果只是将这些工具分别包装为“菜单查询 Skill”“优惠券 Skill”或“下单 Skill”，本质上仍是原有功能的自然语言入口，没有充分体现 Agent Skill 在情境理解、跨系统决策和任务闭环方面的价值。

McMoment 要解决的问题不是：

> 麦当劳现在有什么商品？

而是：

> 在用户此刻的现实情境中，怎样安排一次最合适的麦当劳体验？

这里的“合适”可能同时涉及：

- 是否来得及（基于用户提供的时间）；
- 是否顺路（基于用户提供的位置和目的地）；
- 是否满足热量和蛋白质目标；
- 是否超过当前预算；
- 是否能够使用即将过期的优惠券或积分；
- 是否满足用户提供的多人口味和时间要求；
- 是否有适合参加的主题活动。

## 3. 产品目标

McMoment 的目标是将麦当劳 MCP 从一个“餐饮业务工具集合”升级为一个能够理解现实生活情境的决策与执行代理。

完整服务闭环为：

```text
感知现实情境
    ↓
理解用户目标与约束
    ↓
查询麦当劳真实数据
    ↓
生成并比较候选方案
    ↓
解释推荐理由
    ↓
用户确认
    ↓
创建真实订单或活动预约
    ↓
追踪订单与处理变化
    ↓
向用户反馈结果，并可生成图片化确认材料
```

核心产品目标包括：

1. **减少用户决策成本**：用户不需要逐项选择门店、餐品、优惠券和取餐方式；
2. **提高推荐的真实性**：所有菜单、价格、优惠和可售状态均由麦当劳 MCP 验证；
3. **降低接入复杂度**：优先使用用户在对话中提供的时间、位置、预算和偏好；
4. **形成核心任务闭环**：不仅给建议，还能在确认后执行下单、预约和订单追踪；
5. **辅助结果表达**：通过图片生成将已确认的方案转化为邀请卡或活动海报。

## 4. 核心创新

### 4.1 从“餐品推荐”升级为“情境决策”

McMoment 不只决定“吃什么”，还同时决定：

- 什么时候吃；
- 去哪里吃；
- 送到哪里；
- 选择外送、到店、堂食、外带还是得来速；
- 是否需要预约；
- 如何使用优惠券或积分；
- 是否会影响下一项日程。

### 4.2 麦当劳 MCP 与轻量外部能力组合

麦当劳 MCP 负责提供真实业务事实并完成交易；图片生成能力负责将已确认的方案进行视觉化表达；天气查询能力负责补充当前天气和短时预报。位置和日历由用户设备或宿主系统提供，Skill 只消费这些原生输入，不重复实现地图或日历接入。

| 能力来源 | 主要职责 |
|---|---|
| 麦当劳 MCP | 门店、菜单、营养、优惠、积分、价格、订单和活动 |
| 天气查询 | 当前天气、降雨概率、温度和短时预报 |
| 图片生成 | 生成聚餐邀请卡、亲子任务卡和活动海报 |

除天气查询和图片生成外，本方案暂不接入其他外部系统。位置和日历优先使用用户设备或宿主系统的原生能力，用户也可以直接在对话中提供相关信息。

### 4.3 优惠券与积分成为决策变量

McMoment 不会只展示优惠券列表，而是将优惠券和积分放入统一决策模型中。

例如：

> 在满足 600 千卡和 35 元预算的候选方案中，方案 B 原价较高，但使用今日到期优惠券后实付价从 36 元降至 29 元，因此综合排名从第二名变为第一名。

积分也会作为消费策略的一部分进行比较：

- 使用积分兑换餐券；
- 使用积分兑换商城商品；
- 保留积分；
- 参加积分抽奖；
- 直接现金购买。

涉及积分扣减、商品兑换和抽奖的操作，必须由用户明确确认。

### 4.4 可解释的多目标优化

McMoment 不只给出推荐结果，还会解释：

- 为什么选择这个门店；
- 为什么选择外送而不是到店；
- 为什么选择这套餐品；
- 使用了什么优惠；
- 哪些条件无法完全满足；
- 为什么没有选择另一套方案。

### 4.5 长期个性化

系统可以通过历史订单和完成后的轻量反馈逐步学习：

- 用户真实食量；
- 餐品饱腹感；
- 口味与饮料偏好；
- 是否需要餐具；
- 对价格、时间和营养的优先级；
- 工作日与周末的不同消费习惯；
- 是否愿意为了营养或便利增加预算。

## 5. 三大使用模式

McMoment 不是由多个零散 Skill 拼接而成，而是同一套情境决策引擎在三类生活场景中的表现。

### 5.1 此刻吃什么：个人情境补给

适用于：

- 上班前、会议间隙；
- 健身结束后；
- 通勤途中；
- 加班和夜宵；
- 预算或热量受限；
- 优惠券即将过期。

示例请求：

> 我刚健身完，下午一点有会，午饭控制在 600 千卡和 35 元以内。

系统需要完成：

1. 读取用户提供的当前时间和下一场日程；
2. 读取用户提供的当前位置和会议地点；
3. 查询天气，并结合用户提供的通勤时间选择履约方式；
4. 读取用户提供的运动和营养目标；
5. 查询可用门店和当前菜单；
6. 查询营养信息、优惠券和积分；
7. 生成候选组合并实时计价；
8. 输出最省钱、最适合当前状态和最符合历史偏好的方案；
9. 用户确认后下单；
10. 完成订单追踪并向用户反馈状态。

### 5.2 大家怎么聚：多人组局协调

适用于：

- 办公室团餐；
- 朋友聚会；
- 家庭聚餐；
- 生日和主题活动；
- 临时多人点餐。

示例群聊：

```text
小王：这周找时间聚一下？
小李：周六下午不行。
小陈：我带孩子，最好别太晚。
小张：预算人均 50 吧。
小刘：我最近减脂。
小周：听说麦当劳有主题活动。
```

系统需要完成（群聊内容由用户粘贴或概括提供）：

1. 从群聊中提取参加者、预算、时间和饮食约束；
2. 根据用户提供的信息整理共同空闲时间；
3. 根据用户提供的位置整理门店选择；
4. 查询主题活动和可预约场次；
5. 输出可供群体确认的时间或门店选项；
6. 为不同成员生成餐食方案；
7. 计算总价和人均分摊；
8. 生成群聊确认卡或邀请海报；
9. 生成群聊确认卡或邀请海报；
10. 经负责人确认后预约活动或创建订单。

### 5.3 周末去哪里：城市活动规划

适用于：

- 亲子半日活动；
- 情侣约会；
- 朋友打卡；
- 雨天室内计划；
- 城市限定活动；
- 生日特别任务。

示例请求：

> 周日下午想带 7 岁女儿出去玩，预算 200 元，不想去太远。

系统需要完成：

1. 获取城市、位置和可用时间；
2. 查询天气，并结合用户提供的出行偏好；
3. 查询麦当劳营销活动和主题活动；
4. 查询活动城市、门店、日期和场次；
5. 根据用户提供的距离要求规划简化路线建议；
6. 查询门店菜单并估算餐食预算；
7. 输出两至三个半日方案；
8. 用户确认后完成活动预约；
9. 输出可复制的行程与提醒文本；
10. 生成亲子任务卡或活动邀请卡。

## 6. 核心决策引擎

### 6.1 情境数据模型

McMoment 首先将用户在对话中提供的上下文整理为结构化状态。

```yaml
time:
  current_time: "11:48"
  available_duration: "60min"
  next_event: "13:00 meeting"

location:
  current: "gym"
  destination: "office"
  commute_minutes: 25

environment:
  weather: "rain"
  temperature: 18

health:
  calories_remaining: 600
  protein_target: 30
  workout_completed: true

finance:
  meal_budget: 35
  monthly_food_budget_remaining: 680

social:
  participants: 1
  companion_type: null
```

### 6.2 约束提取

用户的自然语言需求会被转换为硬约束和软偏好。

```yaml
hard_constraints:
  budget_max: 35
  calories_max: 600
  deliver_before: "12:40"
  delivery_address: "office"

soft_preferences:
  protein: high
  sugar: low
  use_expiring_coupon: true
  avoid_rain: true
  familiar_food: preferred
```

#### 硬约束

硬约束原则上不能违反：

- 用户明确预算上限；
- 用户明确时间限制；
- 当前门店实际可售状态；
- 明确忌口与不吃的餐品；
- 参与人数；
- 配送地址与活动场次；
- 用户明确提出的营养上限。

#### 软偏好

软偏好用于候选方案排序：

- 高蛋白；
- 更饱腹；
- 更低价格；
- 使用即将过期的优惠券；
- 使用即将过期的积分；
- 选择历史上喜欢的餐品；
- 减少绕路和等待；
- 减少多人方案中的不公平感。

### 6.3 候选方案生成

候选方案不是由模型凭空生成，而是基于当前门店真实菜单：

1. 获取当前可售餐品；
2. 查询套餐组成及允许替换的商品；
3. 组合主食、小食和饮料；
4. 叠加餐品特制条件；
5. 计算营养总量；
6. 过滤违反硬约束的组合；
7. 叠加优惠券和积分策略；
8. 调用价格计算工具验证最终成交价格。

### 6.4 统一评分模型

候选方案可以使用统一的多目标评分函数：

```text
总分 =
营养适配度 × W1
+ 预算适配度 × W2
+ 优惠利用率 × W3
+ 时间适配度 × W4
+ 历史偏好度 × W5
+ 路线便利度 × W6
+ 多人公平度 × W7
```

不同情境动态调整权重：

| 场景 | 提高的权重 |
|---|---|
| 健身后 | 蛋白质、热量和营养适配度 |
| 会议前 | 时间适配度和履约可靠性 |
| 下雨天 | 外送便利度和路线成本 |
| 月底预算紧张 | 最终实付价格 |
| 优惠券即将过期 | 权益利用率 |
| 多人聚餐 | 多人满意度和公平度 |
| 家庭活动 | 儿童需求、时间和路线便利度 |

### 6.5 推荐解释

每次推荐至少说明：

- 推荐结果；
- 实际价格；
- 营养估算；
- 使用的优惠；
- 推荐该门店和履约方式的原因；
- 未完全满足的条件；
- 与其他方案的主要差异。

示例：

```text
为什么推荐外送：
- 当前正在下雨；
- 你需要在 13:00 前到达公司；
- 外送后的总价仍在预算内。

为什么推荐这套餐：
- 满足 600 千卡上限；
- 蛋白质在候选方案中较高；
- 使用了今日到期优惠券；
- 主食是你过去选择过的口味。

为什么没有选择另一套：
- 虽然便宜 2 元，但蛋白质少 11 克；
- 另一门店需要额外绕路约 18 分钟。
```

## 8. 外部能力设计

当前版本只保留两项轻量外部能力：天气查询和图片生成。日历、地图、健康、群聊、记账、自动化提醒等系统均不作为外部依赖；位置和日历优先使用用户设备或宿主系统的原生能力。

### 8.1 天气查询能力

建议优先接入 Open-Meteo 一类免 API Key 的公开天气接口。调用参数只需要宿主系统提供的经纬度和时间范围，返回当前温度、降雨概率、天气类型和短时预报。

最小接入契约：

```text
输入：latitude、longitude、timezone、forecast_hours
输出：temperature、precipitation_probability、weather_code、forecast_time
```

推荐调用时机：用户提出“现在吃什么”“要不要到店”或“规划户外活动”等请求时查询一次；同一请求内复用结果，不为每个候选方案重复请求。天气结果只保留在当前会话上下文中，不建立长期位置或轨迹记录。

用于：

- 在下雨或极端天气时提高外送、得来速的推荐权重；
- 在用户计划到店时提示天气风险；
- 为亲子活动判断室内或室外方案；
- 在活动海报中展示已查询的天气提示。

接入边界：

- 天气接口不可用时，退回用户主动提供的天气信息；
- 不由 Skill 自己定位用户，只接受设备或用户提供的经纬度；
- 不要求用户注册天气服务，也不在 Skill 内保存 API Key；
- 对接口超时、限流或返回异常统一降级为“天气未知”，不阻塞菜单查询和下单流程；
- 天气只影响推荐排序，不直接替用户改变订单或活动安排。

### 8.2 图片生成能力

用于生成：

- 聚餐邀请海报；
- 活动确认卡；
- 亲子任务卡；
- 城市微旅行路线卡；
- 生日或主题活动邀请卡。

图片生成是辅助表达能力，不代替核心决策与交易流程。

图片生成的输入应来自已经确认的餐食方案、活动信息或订单信息；生成失败时不影响查询、计价和下单流程。

## 9. 典型用户故事

### 9.1 健身后的工作午餐

用户：

> 我下午一点有会，现在刚健身完，帮我安排午饭。

外部上下文：

- 当前时间：11:48；
- 下一场会议：13:00；
- 会议地点：公司；
- 当前天气：下雨；
- 用户位置：健身房；
- 健身房到公司：25 分钟；
- 午餐期望：600 千卡以内；
- 蛋白质目标：30 克以上；
- 今日餐饮预算：35 元；
- 有一张当天到期的优惠券。

系统决策：

1. 用户没有足够时间到店慢慢用餐；
2. 当前下雨，不建议绕路取餐；
3. 配送地址应选择公司而非当前健身房；
4. 订单应安排在会议开始前送达；
5. 餐食需要满足热量、蛋白质和预算条件；
6. 优先测试当天到期优惠券是否能降低符合条件方案的价格。

推荐输出：

```text
我建议送到公司，避免影响 13:00 的会议。

推荐方案：
板烧鸡腿堡 + 玉米杯 + 零度可乐

预计营养：
- 热量：约 570 千卡
- 蛋白质：约 31 克

费用：
- 商品：¥34
- 优惠券：-¥6
- 配送费：¥3
- 实付：¥31

送达地址：公司
预约时间：12:25—12:35

确认后我再提交订单。
```

## 10. 交易安全与确认机制

### 10.1 可直接执行的只读操作

通常可以直接执行：

- 查询门店；
- 查询菜单；
- 查询营养；
- 查询优惠券；
- 查询积分；
- 查询活动；
- 查询订单；
- 查询历史订单；
- 价格试算。

### 10.2 必须确认的状态修改操作

以下操作必须由用户明确确认：

- `create-order`：创建真实点餐订单；
- `cancel-order`：取消订单；
- `mall-create-order`：消耗积分或现金兑换商品；
- `draw-lottery`：消耗积分或次数进行抽奖；
- `party-order-create`：创建主题活动订单；
- `delivery-create-address`：新增用户配送地址；
- `auto-bind-coupons`：修改用户账户中的优惠券状态。

### 10.3 下单确认信息

下单前至少展示：

```text
即将创建真实订单：

门店：××麦当劳
方式：麦乐送
商品：……
优惠：……
配送费：……
实付：¥……
地址：……
预约时间：……
餐具：……
备注：……

是否确认提交订单？
```

积分兑换或抽奖还需要单独提示：

```text
本次将消耗 500 积分，该操作可能无法撤销。
是否确认继续？
```

### 10.4 推荐与事实的边界

- 菜单可售状态必须由麦当劳 MCP 验证；
- 最终价格必须由 `calculate-price` 验证；
- 订单是否创建成功以 MCP 返回结果为准；
- 配送时间只能使用订单或门店返回的信息，不应自行保证；
- 活动名额、场次和适龄信息必须来自真实活动数据；
- 营养推荐仅作为一般参考，不构成医疗建议；
- 缺少过敏原信息时，必须提示用户进一步确认。

## 14. 项目差异化总结

McMoment 与普通点餐助手的核心差异如下：

| 普通点餐助手 | McMoment |
|---|---|
| 等用户说想吃什么 | 理解用户接下来要做什么 |
| 查询菜单 | 理解用户提供的时间、位置、天气和状态 |
| 推荐单个商品 | 进行多目标餐食组合优化 |
| 展示优惠券 | 将优惠券作为决策变量 |
| 只决定吃什么 | 同时决定时间、门店和履约方式 |
| 给出文本建议 | 完成真实计价、下单与预约 |
| 单次对话 | 基于当前对话持续个性化 |
| 面向个人 | 支持多人组局和图片化活动方案 |

## 16. 结论

McMoment 的核心不是为麦当劳 MCP 增加一层自然语言包装，而是利用麦当劳 MCP 作为真实服务执行底座，结合用户主动提供的情境信息、轻量天气查询和图片生成能力，构建一个能够完成餐食决策、交易执行和结果表达的轻量情境决策代理。

其核心价值可以概括为：

```text
理解这一刻
    +
计算最优方案
    +
完成真实服务
```

最终目标是让用户不再需要逐项思考“吃什么、去哪吃、怎么点、用哪张券”，而只需要表达自己的现实状态和目标，其余过程由 McMoment 负责规划、解释和执行。
