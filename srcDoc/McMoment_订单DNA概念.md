# McMoment 订单 DNA 概念

## 1. 核心想法与当前范围

订单即 DNA，餐品即部件，此刻即世界。最终角色由预制的透明部件图拼接，点餐时不调用实时 AI 生图。资源目录保存独立部件，订单保存组合结果与随机种子。

用户点击“继续下单”后，立即根据当前订单生成随机形象或小队；形象跟随 5 秒进度从左向右移动，结束后按钮显示成功，小队播放完成动作。

首版默认堂食，取消原有三个履约动作映射，不再生成履约动作图片。当前页面属于模拟流程：5 秒结束只能表示模拟完成，真实接入后必须以服务端订单结果决定成功，不能用计时器代替真实下单结果。

本文定义目标部件和组装协议，配套《McMoment_餐品部件生图提示词.md》定义制作提示词。协议不等于已实现的资源加载器；目前页面的色块角色仍是占位表现，尚未接入这些 PNG。

## 2. 餐品与部件映射

| 订单分类 | 部件 | 明确边界 |
|---|---|---|
| 主餐 | 身体骨架 body | 只有胸腹、腰胯与连接座；不含头、手臂、腿、装饰 |
| 小食 | 四肢风格 limbs | 一套风格分四张图：左右臂（含手）、左右腿（含脚） |
| 饮料 | 头部 head | 完整头部，包含脸、眼睛、嘴和短颈接口；不含躯干 |
| 甜品 | 装饰 decoration | 翅膀、帽子、光环或披风；不画成独立伙伴 |
| 主餐份数 | 小队人数 | 每一份主餐各生成一名角色，不合并成融合身体 |

例如：板烧鸡腿堡 + 玉米杯 + 零度可乐 + 麦旋风，组合为板烧躯干、玉米四肢、黑银气泡头、奶油翅膀。主餐的“骨架”是可见的躯干外壳，不是人体骨骼图。

同一个餐品在不同套餐里须先按菜单分类和 SKU 标记角色类别。例如麦乐鸡作为主餐与作为小食分别映射 body 和 limbs；不能仅通过名称同时计入两类。

## 4. 图片规格与统一挂点

所有资产采用同一种正面、正交、柔和 2.5D 收藏玩具风格。禁止各张图自行改变透视或左右朝向。生成提示词只能帮助接近尺寸，导入前必须人工或工具裁切、缩放和对齐，不能假设 AI 会精准输出挂点。

每张交付图为 1024 × 1024 透明 PNG，sRGB，边缘干净，保留约 32 px 安全留白。交付图按最终角色画布定位：不把单只手臂放大铺满画面。所有图层以相同原点 (0,0) 叠加。

| 挂点 | 归一化坐标 (x,y) | 1024 px 参考坐标 |
|---|---|---|
| head_mount | (0.50, 0.34) | (512, 348) |
| arm_left_mount | (0.66, 0.42) | (676, 430) |
| arm_right_mount | (0.34, 0.42) | (348, 430) |
| leg_left_mount | (0.59, 0.64) | (604, 655) |
| leg_right_mount | (0.41, 0.64) | (420, 655) |
| back | (0.50, 0.43) | (512, 440) |
| head_top | (0.50, 0.13) | (512, 133) |
| root | (0.50, 0.91) | (512, 932) |

建议身体范围 x=0.32–0.68、y=0.34–0.66，头部 x=0.35–0.65、y=0.14–0.35；四肢从挂点延伸到两侧或脚底，装饰不得超出画布留白。root 是整个人物缩放和跳跃的中心；head_top 是统一装饰定位点，不随不同头部任意漂移。

身体接口需预留约 12–20 px 遮挡余量，由身体或短颈覆盖四肢根部，避免接缝。贴图只烘焙部件自身柔和明暗，不包含地面投影、背景、运动轨迹或外发光粒子。阴影与庆祝星光单独由程序绘制。

建议从后向前固定叠图：back 装饰 → 左右腿 → 左右臂 → 身体 → 头部 → head_top 装饰 → 程序特效。手臂自然垂放到躯干两侧；首版完成动作是向外小幅挥手，避免穿过身体。若后续需要手臂跨胸，另扩展前景手臂层协议。

四肢各为一段可旋转的刚性图层，旋转中心在肩/髋接口，不支持肘膝独立弯曲。头以短颈接口为 pivot；背部和头顶装饰保留各自 pivot。所有 pivot 写入元数据，禁止通过可见挂点圆点标记在图片里。

## 5. 文件与元数据协议

推荐目录：

~~~text
assets/order-dna/
  bodies/{body_id}.png
  limbs/{limb_id}/arm_left.png
  limbs/{limb_id}/arm_right.png
  limbs/{limb_id}/leg_left.png
  limbs/{limb_id}/leg_right.png
  heads/{head_id}.png
  decorations/{decoration_id}.png
  defaults/head_neutral.png
  defaults/arm_left.png
  defaults/arm_right.png
  defaults/leg_left.png
  defaults/leg_right.png
  defaults/body_neutral.png
  catalog.json
~~~

餐品风格共 21 套；实际餐品 PNG 为 6 身体 + 6 × 4 四肢 + 5 头部 + 4 装饰 = 39 张。额外准备 6 张中性基础图（1 身体、1 头、4 四肢），完整基础资源为 45 张。不含动作图片。中性图必须按同一风格和挂点制作，不能拿有餐品特征的图充当中性部件。

catalog.json 是待实现的资源清单；本次新增的是设计协议，当前工程尚无此文件。清单应记录 assetId、文件相对路径、slot、canvas、pivot、drawOrder、接口版本 rigVersion 和来源 SKU 列表。示例：

~~~json
{
  "assetId": "limb_corn_arm_left",
  "file": "limbs/limb_corn/arm_left.png",
  "slot": "arm_left",
  "canvas": [1024, 1024],
  "pivot": [676, 430],
  "drawOrder": 20,
  "rigVersion": "front-v1",
  "sourceSkus": []
}
~~~

sourceSkus 必须由实际菜单数据补齐。上表是设计原型映射，不把名称模糊匹配当作正式 SKU 映射；未识别餐品降级为对应中性部件，仍保留真实餐品名称供说明。

## 6. 小队数量与部件分配

1. 先展开订单：套餐按实际组成拆分，再乘套餐购买数量。主餐人数只数展开后的主餐份数，不把套餐壳再算一次；麦乐鸡一份里的鸡块数不算主餐份数。
2. 主餐每份对应一个稳定 memberIndex 和身体来源。两个相同汉堡也生成两名成员，不去重、不融合。无主餐时显示一名中性基础形象，并明确它不是主餐成员。
3. 小食、饮料、甜品也按份数展开，用订单种子分别打乱后分配。小食份数不足成员数时循环使用本单已有的小食风格；完全无小食时用中性四肢。视觉复用不代表多买一份餐。
4. 每个成员四肢先使用同一套小食风格；若小食份数超过成员数，将剩余小食按 arm_left → arm_right → leg_left → leg_right 顺序轮转替换成员的对应部件，同一槽被多次分配时由最后一次覆盖。这样允许多小食混搭，不增加队员；卡片保留完整餐品列表，不承诺每份食物都能在有限槽位同时可见。
5. 每名成员只有一个头，饮料按打乱后的份数列表循环分配。无饮料使用中性头；多余饮料不会多生头，完整列表在订单信息中保留。
6. 甜品按 back、head_top 分槽。每槽各自按打乱后的可用甜品份数列表循环分配给成员，无可用项则留空；同槽每人最多一件，不叠多顶帽子。
7. 多成员等比例排列成队伍，作为一个整体沿轨道移动；按最左/最右成员的外接边界计算起终点，确保整个小队不越界。大量成员时使用横向可滚动小队区和可见成员数说明，不能静默丢弃主餐份数。

例如：板烧鸡腿堡 ×2、巨无霸 ×1、薯条 ×1、玉米杯 ×1、零度可乐 ×1、派 ×1，生成三名成员，身体为板烧、板烧、巨无霸；四肢在薯条和玉米两种风格间分配，三名都可复用零度头和派帽。每个复用部件仍引用同一个实际订单来源。

## 7. 随机与稳定性

首次点击继续下单时创建一次 draftSeed，并保存当前订单内容快照。memberSeed = hash(draftSeed + memberIndex + 主餐 SKU + rigVersion)。随机只改变本单可用部件的分配、限定配色、装饰选择、命名和完成动画错峰；不得随机选择未点的餐品、改变挂点或翻转单独部件。

同一草稿重复渲染、缩放或进度更新不重新抽样；明确新建一单或修改购物车才换种子。若最终取得真实 orderId，保存已有结果与 orderId 的关联，不因替换 seed 在成功瞬间换脸。

订单模型建议保存：draftId、draftSeed、rigVersion、fulfillment=dine_in、itemsSnapshot、members、status。每个 member 保存 body、四个 limb 槽、head、两个 decoration 槽及各部件对应的餐品来源或 neutral 标记。

## 8. 5 秒进度与完成动作

| 时点 | 按钮 | 下方形象与进度 |
|---|---|---|
| 点击前 | 继续下单 | 不生成本单随机角色，可显示中性说明占位 |
| 点击瞬间 | 下单处理中，禁用重复点击 | 生成并锁定小队，出现 0% 进度 |
| 0–5 秒 | 下单处理中 | p=clamp(elapsed/5000,0,1)，进度填充与小队位置共用 p |
| 5 秒结束（模拟） | 模拟下单成功 ✓ | 100%，小队停稳，播放一次庆祝动作 |
| 真实接口接入后 | 订单成功或失败 | 真实成功才显示“下单成功”；未完成则等待，失败可重试 |

布局从上到下：订单摘要 → 下单按钮 → 进度条及其下方的小队。进度计时以真实经过时间计算，推荐 requestAnimationFrame + performance.now，避免累计 interval 次数造成漂移。新订单或离开页面需清理动画，过期回调不得更改新订单。

完成动作不需要额外生图：整队轻跳 10–16 px、落地轻微缩放恢复，一侧手臂围绕肩点向外挥动约 12°，装饰轻摆并出现独立星光。持续约 700–900 ms 后回到稳定姿态，多成员依次延迟约 60 ms。减少动态效果设置下保留成功状态与静态星光，关闭位移/跳跃。

默认堂食只影响流程文案，不强制添加托盘、桌椅或举杯道具，不重新引入履约动作映射。

## 9. 生成与验收

先制作中性基础角色并确认拼接，再制作 6 个身体与其他风格。每张图按配套提示词单独生成，后处理到统一画布与挂点。21 套指风格类别，四肢需逐张执行提示词，不可一次请求 21 格或四肢拼图。

验收必须检查：透明 alpha、接缝无白边、同尺寸叠图可拼接、所有头与身体兼容、各四肢接口兼容、两种装饰槽不遮脸、完成挥手不脱节。通过中性 rig 后随机抽取至少三组跨风格组合，并验证两份相同主餐、无饮料、无小食、无甜品、只有小食、多人及套餐数量展开等场景。
